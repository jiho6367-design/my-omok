# H8 큰 사각형: 양쪽 자동 15초 대결과 방어 검사

2026-10-26. 첫 수는 흑 H8, 둘째 수는 F6–J10 테두리 16곳으로 고정했다. 이후 양쪽 모두 앱의 자동 모드(최대 15초)를 사용했다. 자동 모드의 국면별 예산과 조기 완료를 그대로 적용하므로 매번 15초를 소비하는 실험은 아니다. 고정한 두 돌은 엔진의 추천으로 세지 않았다.

## 실행과 판정

- 실제 공개 HTML을 별도 Edge 컨텍스트에서 실행했다. 동일한 채택 모델, CPU 패턴 테이블, navigator concurrency 8, 게임당 Worker 풀 3개와 직렬 Worker를 사용하고 최대 두 판을 동시에 진행했다. 예측 탐색·입력 지연·대국 시계는 껐다.
- 합법적인 정확한 5목이 실제 착수되거나 판이 찬 경우만 완료로 판정했다. 점수·PV·강제승 표시로 대국을 조기 판정하거나 수순 상한으로 무승부 처리하지 않았다.
- 각 착수의 국면, 응수, 완료 비교, 검사 결과, 시간, 모드와 모델 식별자를 fsync된 해시 연결 JSONL과 원자적 체크포인트에 보존했다. 보고서는 착수·합법성·PV·모드별 적용 예산·실제 종료를 다시 검사한다.
- 원본 양쪽 자동 16판(v5.18.5), 중간 수정본(v5.18.6), 최종 탐색본(v5.18.7)을 서로 다른 디렉터리에 보존했다. 중간본은 시간 배분 결함 발견 후 **6판 완료·10판 중단**으로 저장했으며 완전한 대회로 계산하지 않는다.

이전의 선공 빠르게 1초/후공 자동 15초에서는 후공이 16판 모두 이겼다. 선공도 자동으로 바꾼 원본 엔진에서는 후공 1승·15패였다. 이는 모드와 비교군을 구분해야 하는 근거이며, 선후공의 일반적인 필승 여부를 증명하지 않는다.

## 확인한 결함과 수정

### 4목과 두 번의 준비 수가 연결되는 공격

원본 G6 대국의 `H8 → G6 → I7 → F7 → H5 → G8 → H9 → G9`에서 백 8수 G9 뒤 흑 H6의 4목, 준비 수 G5, 백의 반격 4목에 대한 필수 차단, 후속 4목, 두 번째 준비 수 F5가 연결된다. 흑 H6은 자식 후보 16개 중 두 번째에 이미 있었으므로 후보 누락으로 분류하지 않았다. 동일 모델의 차가운 탐색으로 원래 깊이 7의 점수와 PV도 재현했다.

준비 수 한 번만 허용한 기존 검사로는 이 수순을 증명하지 못했다. 준비 수 두 번을 허용한 제한 탐색은 상대의 모든 합법적 방어를 포함한 강제승 인증서를 만들었고, 별도 검증기가 6,237개 DAG 노드와 7,662개 방어를 검사했다. 흑 H6이 실제 놓인 다음에는 백의 합법적 216수 모두 패배한다는 인증서도 별도로 검증했다. 이와 대칭인 원본 8대국의 백 8수 직후 국면과 실제 흑 9수도 D4 변환과 정확히 일치했다.

`preparationTrap`을 직렬·심층·병렬 최종 후보 검사에 연결했다. 실시간 분석과 실험 JSONL에는 공격자·방어자·진입 국면·준비 수 한도·완료 여부와 전체 인증서를 보존하며, 실제 반증된 후보만 제외한다. 새 앱 기보에는 아래 저장 용량 수정에 따라 비검증 요약을 남긴다. 첫 후보에 검사 예산의 65%를 우선 배정하고 나머지는 남은 시간 안에서 검사한다. 실제로 이미 이긴 착수는 가상 상대 차례로 반증하지 않는다.

고정 G6 백 8수의 원본 앱은 G9를 추천했고, 수정 앱은 G9를 증명으로 제외하고 H6을 추천했다. H6 및 I6에서 제한 검사로 상대 강제승을 찾지 못한 사실은 **안전·필승의 증명이 아니다**. 최종 완전대국에서도 초기 함정 회피가 최종 승리를 보장하지 않았다.

### 불리한 국면의 남은 시간 사용

중간본 G6의 백 18·20·22·24수는 깊이 10까지 완료하고 약 7.12·9.64·8.56·4.66초에 끝났다. 추가 준비 공격 검사는 약 650ms에서 미완료로 중단되었다. 15초 상한 안에 시간이 남아 있어도 더 깊은 비교나 방어 검사에 쓰이지 않는 문제가 확인됐다.

- 자동 반복 심화와 병렬 비교의 최대 완료 깊이를 10에서 16으로 확장했다. 기존 수당 시간 상한은 유지한다.
- 안정적인 음수 점수를 쉬운 국면의 조기 종료 근거로 사용하지 않는다. 양수 국면의 기존 안정 종료는 유지한다.
- 불리한 미해결 병렬 국면은 남아 있는 원래 방어 마감 시각까지 검사할 수 있다. 준비 수 검사의 고정 650ms 제한을 없애고 후보별 실제 배정 시간을 사용한다.
- 완료된 비교 결과와 증명된 반증은 유지하고, 진행 중인 후보가 시간 초과로 최종 추천을 덮어쓰지 않게 하는 기존 계약을 유지한다. 확정 승리의 즉시 종료도 유지한다.

같은 중간 G6 백 22수의 새 브라우저 비교에서 원본 중간본은 H9·완료 깊이 10·12,371ms, 최종본은 H9·완료 깊이 11·13,973ms였다. 같은 수라도 추가 비교를 완료했다는 근거다. 두 결과 모두 미해결이므로 전술적 안전이나 승리의 근거로 쓰지 않았다. 중간본의 이 후속 수순에서는 최초 회피 가능 분기점을 아직 증명하지 못했다.

평가 함수·탐색 말단·신경망 입력·규칙은 바뀌지 않았다. `node-v4` 전이표 의미도 유지되며 엔진 식별자에는 `preparation-2-iterative-16`을 추가했다. 검사 결과 미완료, 제한 범위 내 미발견, 증명된 패배를 구분한다.

## 검사와 한계

- 최종 탐색 소스의 엔진 회귀 검사 **62개 통과**. 새 준비 공격 검사는 회전·반사와 색 교환 16경우, 인증서 전체, 정확한 5목·장목·기한·보드 복구를 확인했다. 실제 최종 후보 검사의 두 색 통합 사례도 통과했다.
- 실제 스케줄러의 생성 fixture에서 불리한 국면의 깊이 16 진입, 쉬운 양수의 깊이 4 종료, 깊이 11 미완료 시 깊이 10 결과 보존, 최종 방어 예산과 하드 마감 시각을 검사했다. 이 검사는 기력 평가가 아니다.
- 실제 공개 HTML의 병렬 Worker, 필수 4목 차단(352경우), 승리 즉시 추천(16), 3·3 유도(10), 저항·시간 초과(8), 후보 승리(8) UI 회귀 검사를 통과했다.
- 원본 15패의 백 231차례에서 합법적인 유일 즉시 5목 차단을 놓친 사례는 0개였다. 따라서 이번 결함을 단순한 즉시 4목 방어 누락으로 설명하지 않는다. F10 원본 후보 제외 1,081개 중 1,080개 인증서를 재검증했고, 한 건은 증거 부족으로 남겼다. 확인된 잘못된 인증서는 없었다.
- 최종 16패의 백 254차례에서도 유일 즉시 방어 누락은 0개였다. 각 판의 실제 국면에 연결되는 저장 증명 16개를 독립 검증했다. 10개는 실제 흑 응수의 모든 합법적 방어 증명, 1개는 VCF, 5개는 실제 선택된 백 16수 뒤 준비 공격 증명이다. 마지막 5개에서 증명의 첫 흑 수와 실제 다음 흑 수는 다르므로 실제 대국이 그 증명 경로를 그대로 따랐다고 해석하지 않는다. 지는 국면이 확인된 시점과 최초 회피 가능 실수는 구분한다.
- 준비 수 세 번으로 확장한 제한 진단도 후속 패배의 개선을 입증하지 못했다. 특정 좌표를 외우는 예외나 확인되지 않은 확장을 추가하지 않았다. 후보 하나의 패배 증명을 전체 국면의 강제패배로 올리지 않으며, 제한 탐색의 미발견을 안전으로 표시하지 않는다.
- 각 시작점 한 판이며 대칭 국면도 포함한다. 양쪽 모두 같은 수정 엔진을 쓰므로 승패 차이를 후공 방어만의 인과 효과나 전체 기력 향상으로 해석할 수 없다.

## 기보 저장의 용량 회귀 수정

새 준비 공격의 전체 인증서를 앱의 새 착수 기록에도 복사하면 기보 네 판에서 Edge 저장 한도를 넘는 현상을 별도의 비영구 브라우저 컨텍스트에서 재현했다. 기존 세 판의 저장 바이트는 유지됐지만 네 번째 판 저장은 `QuotaExceededError`로 실패했다.

배포본은 `src/app.js`의 새 착수 스냅샷에 한해 `preparationTrap.proof`를 명시적인 비검증용 요약으로 저장한다. `certificateRetained:false`와 `independentlyVerifiable:false`를 남기며, 실시간 전체 분석, 기존 저장 기보, 다른 승리 인증서와 실험 원본은 변경하지 않는다. 같은 실제 다섯 기보로 저장과 다시 읽기를 확인했다. 생성 fixture는 실제 commit 경로, 기존 이벤트 불변, 전체 증명 비순회, 일반 분석 및 승리 증명 보존을 검사한다.

이 저장 처리만 최종 대국을 동결한 뒤 바뀌었다. 최종 대국의 위 소스·HTML 식별자를 배포본으로 다시 표기하지 않는다. 배포 식별자와 동결본 대비 소스 차이는 로컬 `after.json`에 별도로 기록한다. 엔진·Worker·시간 설정·모델은 동결 대국과 동일하다.
