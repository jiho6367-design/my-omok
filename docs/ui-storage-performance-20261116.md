# v5.18.67 저장 기보와 결과 전달 지연 개선

저장 기보가 쌓일수록 착수·목록 열기에서 전체 기록의 JSON 복제, 변경 비교, 복구 기록 생성이 반복됐습니다. 분석 결과를 화면에 전달하는 과정에도 같은 방어 결과의 중복 검사와 같은 원시 결과의 중복 인코딩이 있었습니다.

## 저장된 게임 최대 10개

게임 날짜 기준 최신 10개를 유지하고 오래된 게임부터 목록과 정본 저장 데이터에서 제거합니다. 현재 계속 두는 게임은 오래됐어도 10개 안에 남깁니다. 열기·저장·가져오기·여러 창의 변경 병합·복구 기록 재생에 같은 제한을 적용합니다. 복구 변경은 순서대로 모두 재생한 뒤 제한을 적용합니다. 일반 저장은 남길 게임만 직렬화하고, 기보 복원·가져오기는 남길 게임의 착수만 검증합니다.

남긴 게임의 착수·추천·증명 메타데이터는 유지합니다. 독립된 등록 기보, 학습 기록, 마이그레이션 원문과 충돌 복구 자료, 별도 증명 보관소도 보존합니다. 저장 실패 시 마지막 저장 원문과 복구 기록을 유지하고 오류를 표시합니다.

## 같은 생성 입력으로 측정한 결과

같은 PC의 Edge 157 headless 새 컨텍스트에서 v5.18.66과 v5.18.67을 비교했습니다. 입력은 합법적인 24수 생성 기보 100개, 판마다 16KiB의 생성 메타데이터이며 JSON 크기는 1,865,558바이트입니다. 사용자 브라우저 프로필·저장 공간은 읽지 않았고 엔진 탐색도 실행하지 않았습니다. 각 버전 3회, 반복 저장은 총 9회의 중앙값입니다.

동일한 100판 입력 중 최신 10판만 남기는 보존 정책의 효과가 포함된 측정입니다. 최신 날짜 10개, 오래된 현재 게임 보호, 남긴 메타데이터와 저장 완료를 확인했습니다. 첫 화면 렌더와 큰 단일 기보의 복제 비용은 남아 있습니다. 이 결과는 해당 생성 입력의 측정이며 모든 PC의 체감 속도나 사용자 렉의 유일한 원인을 입증하지 않습니다. CDP에서 직접 실행한 미세 측정은 Long Task 관찰에 모두 잡히지 않아, 표에는 직접 잰 동기 실행 시간을 사용했습니다.

## 증명 조회와 결과 전달

증명 후속 조회와 내보내기는 `followed` 저장소의 전체 조회 대신 `gameId` 인덱스로 해당 판의 행을 읽습니다. 생성 자료를 사용한 실제 IndexedDB 검사에서 전체 조회는 241행이었고, 판별 인덱스 조회는 각각 2행·1행이었습니다. 기존 데이터베이스를 올릴 때 원시 바이트와 메타데이터를 보존하며, 다시 열었을 때 전체 증명 재검증도 유지합니다. 이 행 수는 조회 범위 검사 결과이며 시간 단축 비율을 뜻하지 않습니다.

최종 결과는 외부 완료 콜백 전에 계속 검증합니다. 같은 콜백 안에서 판·차례·게임·정책·후보·평가·증명 내용이 그대로인 작고 제한된 결과는 이미 끝낸 검사를 재사용합니다. 큰 결과, 깊은 구조, 변경된 증거, 이후의 전달과 복기는 기존 검사를 다시 수행합니다.

같은 원시 결과 콜백에서 처음 결과와 첫 승리 결과를 함께 보관하는 경우에는 동일한 정규 바이트를 두 출처 범위에 재사용합니다. 두 범위의 출처 정보와 별도로 선택한 최종 결과는 유지합니다. 생성한 6,000노드 전송 자료에서 콜백 반환 전 인코딩은 3회에서 2회로 줄었습니다. 증명 내용을 다시 쓰거나 출처 검증을 생략하지 않으며, 이 단일 자료의 소요 시간으로 일반적인 속도 향상 비율을 주장하지 않습니다.

관련 회귀 검사는 `game-retention`, `game-retention-ui`, `live-proof-store-index-ui`, `analysis-delivery-finalization`, `live-proof-capture-reuse`입니다. 이번 변경은 저장과 UI 전달 경로에 한정됩니다. 엔진 본체·분석 Worker·평가기·기존 모델과 무적수·동등수 자료 및 선택 동작은 유지합니다.
